A self-assessment I try to keep honest, because nothing's worse in an interview
than claiming expert and getting found out.

**Strong / would happily be tested on:**
- Go. Three years daily, idiomatic, comfortable with concurrency patterns
  (channels, worker pools, context cancellation), profiling with pprof.
- Postgres / MySQL. Schema design, indexing, reading query plans, writing
  non-trivial SQL, understanding isolation levels and where they bite.
- Designing CRUD-plus-business-logic services and REST APIs. My bread and butter.
- Debugging production issues, reading logs and metrics, being on call.

**Competent / used in real work but not deep:**
- Kafka and Redis — I've used them in anger but I'd call myself a competent user,
  not someone who deeply understands their internals.
- AWS (ECS, RDS, S3, SQS). I can operate in it; I'm not an infra specialist.
- Python — for scripts and data transforms, not for big systems.
- Docker, basic CI/CD, Terraform that someone else mostly wrote.

**Weak / honest gaps:**
- Kubernetes — I can read a manifest and deploy, but I've never run a cluster.
- Frontend — I can hack on React enough to be dangerous, that's it.
- Algorithms / competitive-programming-style problems — average. I prep for the
  LeetCode portion of interviews and it's the part I dread.
- Large-scale distributed systems — consensus, sharding, multi-region. I
  understand the concepts from reading; I haven't built them.
- ML / data engineering — basically none.

If you ask me something in the "strong" list, dig as deep as you want. If you ask
me something in the "weak" list, I'll tell you the boundary of what I actually
know rather than bluff.
